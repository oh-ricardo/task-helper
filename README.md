# Task Helper

Интерактивный технический прототип по `PRD-voice-to-yandex-tracker.md`.

Архитектура и контуры развёртывания: [docs/architecture.md](docs/architecture.md).

## Что реализовано

- Текстовый ввод и редактирование исходного текста.
- Локальное формирование черновика: заголовок, структурированное описание, дедлайн, приоритет, участники и спринт.
- Профили маршрутизации с обязательной доской.
- Выбор текущего, следующего и следующего через один спринта по календарным датам.
- Блокировка создания без обязательного спринта.
- Просмотр источника значений, уровня уверенности и истории созданных демо-задач.
- Регистрация и вход нескольких пользователей по email; у каждого — отдельные профиль, маршрутизация и подключение Tracker.
- Форма подключения Яндекс Трекера с хранением OAuth-токена в PostgreSQL только в зашифрованном виде.
- Получение проектов, досок и неархивных спринтов из подключённого Tracker.
- Сохранение очереди, проекта, доски и спринта по умолчанию для новых задач.
- Создание реальных задач в Tracker с защитой от повторной отправки.

## Запуск

Установите зависимости и настройте локальную БД по [.env.example](.env.example). Пароль в `.env` не коммитится.

```powershell
npm install
npm run db:migrate
```

Запустите сервер:

```powershell
npm start
```

После запуска зарегистрируйте аккаунт: укажите имя, email и пароль не короче 12 символов. Каждый аккаунт видит только собственные настройки, подключение к Tracker и историю задач в этом браузере.

## Пользователи и настройки

Пользователь может:

- зарегистрироваться и войти по email и паролю;
- изменить имя, email, часовой пояс и приоритет новых задач;
- подключить собственный аккаунт Яндекс Трекера;
- выбрать собственные очередь, проект, доску и спринт по умолчанию.

Данные учётной записи хранятся в `users`, пользовательские настройки — в `user_settings`, а данные Tracker — в записях, связанных с `user_id`. OAuth-токен одного пользователя не доступен другому пользователю и не возвращается браузеру.

### Переход с однопользовательской версии

Запустите `npm run db:migrate` перед развёртыванием новой версии. Миграция добавляет email и имя существующему пользователю, не меняя его `user_id`, поэтому сохранённые Tracker-подключение и настройки маршрутизации остаются привязаны к нему.

Войти в такой аккаунт можно прежним паролем, оставив email пустым. Затем сразу укажите настоящий email в разделе «Настройки по умолчанию» → «Мой профиль».

## Продакшен в Timeweb

Приложение развёртывается из ветки `main`: после `git push origin main` Timeweb App Platform запускает автодеплой. Для production требуется PostgreSQL: файловый fallback предназначен только для локального запуска.

1. Создайте PostgreSQL DBaaS и отдельную БД для приложения.
2. Включите публичный IPv4 базы и обязательный TLS, если App Platform не подключён к той же приватной сети. После этого укажите в `DATABASE_URL` внешний хост базы.
3. Выполните миграцию один раз с машины, имеющей доступ к базе: `npm run db:migrate`.
4. В панели Timeweb задайте переменные окружения и перезапустите приложение.

```text
DATABASE_URL=postgresql://<user>:<url-encoded-password>@<host>:5432/<database>
DATABASE_SSL=true
HOST=0.0.0.0
COOKIE_SECURE=true
TRACKER_ENCRYPTION_KEY=<base64-encoded-32-byte-key>
GIGACHAT_CREDENTIALS=<authorization-key>
GIGACHAT_SCOPE=GIGACHAT_API_PERS
GIGACHAT_MODEL=GigaChat-2-Pro
GIGACHAT_BASE_URL=https://gigachat.devices.sberbank.ru/api/v1
LOG_LEVEL=info
```

Не храните строку подключения, OAuth-токены, ключ шифрования и ключ GigaChat в Git или документации. После замены хоста, пароля или иных переменных окружения приложение нужно перезапускать. Подробный порядок и диагностика — в [docs/architecture.md](docs/architecture.md#продакшен-в-timeweb).

## Логирование

Сервер выводит JSON-логи в stdout/stderr: запуск, завершение HTTP-запроса с `requestId` и длительностью, события авторизации, операции Tracker, создание черновиков и ошибки интеграций. Уровень задаётся переменной `LOG_LEVEL` (`debug`, `info`, `warn`, `error`; по умолчанию `info`).

Значения полей с токенами, паролями, ключами, cookie и зашифрованными данными заменяются на `[REDACTED]`. Для диагностики стеки ошибок можно включить только при необходимости: `LOG_STACKS=true`.

### События

- `server.started` — запуск сервера: хост, порт и тип хранилища.
- `http.request_completed` — завершённый HTTP-запрос: `requestId`, метод, путь, код ответа и длительность в миллисекундах.
- `http.request_unhandled_error` — необработанная ошибка запроса: `requestId`, метод, путь и сведения об ошибке.
- `auth.registration_completed`, `auth.login_completed`, `auth.logout_completed` — регистрация, успешный вход и выход; для успешных действий указывается идентификатор пользователя.
- `auth.login_rejected`, `auth.registration_failed`, `auth.login_failed` — отклонённый вход и ошибки работы с авторизацией.
- `tracker.connection_saved`, `tracker.connection_tested`, `tracker.connection_deleted` — сохранение, успешная проверка и удаление подключения к Tracker.
- `tracker.defaults_saved` — сохранение маршрутизации по умолчанию; фиксируется только наличие очереди, проекта, доски и спринта.
- `tracker.issue_created` — создание задачи: ключ задачи, очередь, приоритет и факт назначения проекта или спринта.
- `draft.generated` — успешно сформированный черновик: идентификатор пользователя и длина исходного текста.
- `tracker.request_failed`, `tracker.request_rejected`, `gigachat.request_failed` — сетевые ошибки и отклонённые ответы внешних API.
- События с суффиксом `_failed` для Tracker и `draft.generation_failed` — ошибки операций приложения.
- `process.unhandled_rejection`, `process.uncaught_exception` — необработанные ошибки процесса; после `uncaught_exception` сервер завершает работу с кодом `1`.

Во все события, созданные при обработке HTTP-запроса, автоматически добавляется `requestId`, чтобы связать действия и ошибки одного запроса.

## Граница прототипа

Пользователь регистрируется по email, имени и паролю от 12 символов. Хеш и уникальная соль сохраняются в PostgreSQL; без него действует временный файловый fallback `.data/auth.json`. Хеширование использует PBKDF2-SHA-512, браузер получает только `HttpOnly`, `SameSite=Strict` сессию на 8 часов. Настройки профиля (имя, часовой пояс, приоритет), маршрутизация и подключение Tracker изолированы по пользователю. Файл с данными и `.env` исключены из репозитория.

Для внешнего развёртывания обязательны HTTPS и переменная `COOKIE_SECURE=true`. Новая задача создаётся в Tracker с OAuth-токеном пользователя после явного подтверждения в интерфейсе.

## Подключение Яндекс Трекера

В разделе «Подключение» пользователь указывает OAuth-токен, ID организации и её тип. Для Яндекс 360 используется `X-Org-ID`, для Yandex Cloud / Identity Hub — `X-Cloud-Org-ID`.

Перед сохранением подключения задайте отдельный ключ шифрования в `.env` и в переменных окружения продакшена:

```powershell
node -e "console.log(require('node:crypto').randomBytes(32).toString('base64'))"
```

Сохраните полученное значение как `TRACKER_ENCRYPTION_KEY`. Сервер шифрует весь набор параметров подключения алгоритмом AES-256-GCM перед записью в таблицу `tracker_connections`; открытый токен не возвращается API и не хранится в браузере. Потеря или замена этого ключа сделает ранее сохранённые подключения нечитаемыми.

Кнопка «Проверить подключение» отправляет серверный запрос `GET /v3/myself` к API Tracker. Браузер получает только результат и отображаемое имя аккаунта, OAuth-токен в запросе браузера не участвует.

Раздел «Настройки по умолчанию» содержит профиль пользователя и настройки Tracker. Профиль хранит имя, email, часовой пояс и приоритет новых задач. Он определяет часовой пояс для относительных дат и приоритет, когда он не определён в тексте. Раздел запрашивает `GET /v3/queues`, `GET /v3/projects`, `GET /v3/boards` и спринты выбранной доски. Выбранные значения сохраняются в `tracker_defaults`; при формировании черновика по умолчанию используется выбранный спринт.

Кнопка «Создать в Tracker» отправляет `POST /v3/issues` с очередью, проектом, спринтом, заголовком, описанием, приоритетом и датами. Для каждого черновика формируется параметр `unique`, который предотвращает повторное создание при повторной отправке.

Черновик формирует GigaChat через серверный endpoint. Ключ GigaChat хранится только в `.env`; клиентский JavaScript его не получает. Для HTTPS-соединения используется сертификат НУЦ Минцифры из `certs/`.
