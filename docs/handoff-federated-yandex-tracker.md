# Передача разработки: федеративный Yandex Tracker

Дата: 2026-10-01.

## Контекст и принятое решение

Организация использует федеративный аккаунт. OAuth-токены для интеграции Tracker недоступны. Единственный допустимый способ — сервисный аккаунт Yandex Cloud:

1. Сервер подписывает JWT авторизованным ключом сервисного аккаунта.
2. JWT обменивается в Yandex IAM на краткоживущий IAM-токен.
3. Tracker API вызывается с `Authorization: Bearer <IAM-токен>`.

Это уже реализовано в текущей рабочей копии. Не возвращайте форму OAuth и не сохраняйте токены пользователей в БД.

Организация для запросов Tracker:

```text
X-Cloud-Org-Id: bpf7jl9ghb35o2idt8iq
```

## Что изменено

- `lib/yandex-iam.js` — выпуск JWT, обмен на IAM-токен, кэш токена и заголовки Tracker.
- `server.js` — все вызовы Tracker переведены с `OAuth` на `Bearer` IAM; удалены endpoints сохранения и удаления пользовательского OAuth-подключения.
- `index.html`, `app.js` — убраны поля OAuth и ID организации. В интерфейсе осталась проверка серверного подключения.
- `.env.example`, `README.md`, `docs/architecture.md`, `PRD-voice-to-yandex-tracker.md` — обновлены под сервисный аккаунт.
- `scripts/migrate.js` больше не создаёт таблицу `tracker_connections`.

## Реализация аутентификации

Файл: `lib/yandex-iam.js`.

Секретная переменная `YANDEX_TRACKER_SERVICE_ACCOUNT_KEY` содержит base64 от содержимого JSON авторизованного ключа. Ожидаемые поля JSON:

```json
{
  "id": "<public-key-id>",
  "service_account_id": "<service-account-id>",
  "private_key": "-----BEGIN PRIVATE KEY-----\\n..."
}
```

Допускается также передать сам JSON строкой, но для панели переменных окружения предпочтителен base64: это исключает проблемы с переносами строк в `private_key`.

JWT содержит:

```json
{
  "typ": "JWT",
  "alg": "PS256",
  "kid": "<id>"
}
```

```json
{
  "iss": "<service_account_id>",
  "aud": "https://iam.api.cloud.yandex.net/iam/v1/tokens",
  "iat": "<unix-time>",
  "exp": "<iat + 3600 seconds>"
}
```

Подпись создаётся встроенным `node:crypto` с RSA-PSS и SHA-256; сторонняя JWT-библиотека не нужна. JWT отправляется в:

```text
POST https://iam.api.cloud.yandex.net/iam/v1/tokens
Content-Type: application/json

{"jwt":"<JWT>"}
```

Ответный `iamToken` хранится только в памяти процесса. При наличии `expiresAt` срок кэша сокращается на пять минут; после перезапуска токен запрашивается заново. Параллельные запросы используют один незавершённый обмен (`tokenRequest`).

## Конфигурация на корпоративном ПК или сервере

1. Получить JSON авторизованного ключа сервисного аккаунта из корпоративного защищённого канала. Не отправлять его в чат, не добавлять в Git и не помещать в документацию.
2. Преобразовать файл в base64 в PowerShell:

```powershell
[Convert]::ToBase64String([IO.File]::ReadAllBytes('C:\secure\service-account-key.json'))
```

3. Сохранить результат только как секрет окружения:

```text
YANDEX_TRACKER_SERVICE_ACCOUNT_KEY=<base64-encoded-authorized-key-json>
YANDEX_TRACKER_ORG_ID=bpf7jl9ghb35o2idt8iq
```

`YANDEX_TRACKER_ORG_ID` необязательна: это значение уже задано в коде по умолчанию. Она оставлена исключительно для другого корпоративного контура.

Для локальной разработки скопировать `.env.example` в `.env` и добавить эти переменные. Файл `.env` исключён из Git.

## Обязательная настройка в Tracker

Создания сервисного аккаунта в Yandex Cloud недостаточно. До первого реального запроса нужно:

1. Обратиться к `anna.anisimova@effem.com`, чтобы сервисный аккаунт стал виден в Yandex Tracker.
2. Добавить сервисный аккаунт в пилотные очереди.
3. Выдать минимально необходимые права: чтение справочников и создание задач в нужных очередях.
4. Уточнить обязательные локальные поля каждой очереди. Текущий код отправляет `summary`, `queue`, `description`, `markupType`, `priority`, опционально `start`, `deadline`, `project`, `sprint` и `unique`.

## Как проверить

После задания переменных и перезапуска:

1. Войти в приложение.
2. Открыть «Подключение» и нажать «Проверить подключение».
3. Успешный запрос вызывает `GET https://api.tracker.yandex.net/v3/myself` от сервисного аккаунта.
4. В «Настройки по умолчанию» загрузить очереди, проекты и доски.
5. Создать тестовую задачу только в согласованной тестовой очереди.

Ожидаемые ошибки:

| Симптом | Причина и действие |
| --- | --- |
| `отсутствует ключ сервисного аккаунта` | Не задана `YANDEX_TRACKER_SERVICE_ACCOUNT_KEY`. |
| `Ключ ... имеет неверный формат` | В переменной не base64 JSON или в JSON отсутствуют `id`, `service_account_id`, `private_key`. |
| `Yandex IAM отклонил JWT` | Неверный/отозванный ключ, ключ не принадлежит аккаунту, неверно переданы переносы строки. |
| Tracker 401 | IAM-токен не принят; проверить ключ и время сервера. |
| Tracker 403 | Сервисный аккаунт ещё не виден в Tracker или у него нет прав на организацию/очередь. |

## Безопасность

- Не логировать `YANDEX_TRACKER_SERVICE_ACCOUNT_KEY`, JWT, IAM-токен, cookies, пароли и строку подключения к БД.
- Не добавлять ключ в `.env.example`, README, issue или commit.
- При утрате ключа отозвать его в Yandex Cloud, создать новый, заменить секрет окружения и перезапустить приложение.
- Старые развертывания могли иметь таблицу `tracker_connections` с зашифрованными OAuth-параметрами. Новый код её не читает и новые миграции её не создают. Не удалять её автоматически: сначала согласовать с владельцем данных. После подтверждения, что старые подключения не нужны, удалить таблицу отдельной миграцией.

## Проверки, выполненные локально

Успешно выполнено:

```powershell
node --check server.js
node --check lib\yandex-iam.js
node --check app.js
```

Также выполнен изолированный тест: сгенерирована временная RSA-пара, JWT проверен публичным ключом как PS256, проверены `Authorization: Bearer iam-token` и `X-Cloud-Org-Id`. Реального запроса в Yandex Cloud не было: авторизованный ключ и права сервисного аккаунта в рабочую среду не передавались.
